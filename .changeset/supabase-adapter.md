Add a Supabase adapter as the optional `@richardmcquiston01/storage-adapters/supabase` entry point. `supabaseAdapter({ client, table?, schema?, onWatchError? })` keeps each key as a row in a PostgreSQL table, reached through the `supabase-js` client, with a counter `revision`. `supabaseSetupSql({ table?, schema? })` returns the SQL to run once: the table (UUID id, value, revision, timestamps), row-level security turned on with no policies, the key's unique index as the replica identity (so a Realtime delete carries the key and nothing else), the table in the `supabase_realtime` publication, and two functions the adapter calls through `rpc`: `<table>_set`, which checks the revision and writes in one statement (so two writers holding the same revision cannot both win, and a key with nothing stored is created), and `<table>_list`. No SDK is bundled; the real `supabase-js` client type-checks against `SupabaseClientLike` without casts. `list` pages through the results until the server has nothing more, so it works under the project's row limit. `subscribe` reports your own writes and, through one Realtime `postgres_changes` channel on the table, changes other clients make, once each. PostgREST errors map to `forbidden` (including row-level security and bad keys), `quota`, `invalid` (a missing table or function says to run the setup SQL; text PostgreSQL cannot hold) and `unavailable`, and messages name the key. Row-level security policies stay your job.
