# Export audit (1.0 readiness)

Every export of `@richardmcquiston01/storage-adapters`, with a label for 1.0.

> **Decided (2026-10-19).** The split below was approved, `restAdapter` counts as Stable, `compareKeys`, `keysWithPrefix` and `DEFAULT_MAX_BYTES` stay public and are documented in the README, and the five Internal helpers are no longer exported. Two things changed after this audit was written, in 0.15.0: the `./react` entry point (`useStoredValue`) was added and is **Experimental** (it is tested with `react-test-renderer` only, and has had no time in a real app), and `yamlFileAdapter` gained `keepComments` and the `YamlDocumentLike` type (Stable, with its adapter). The tables below are the original proposal.

- **Stable:** covered by semver from 1.0. A breaking change needs a new major version.
- **Experimental:** exported and documented as experimental. It may change in a minor release, and the changelog says so. It moves to Stable in a later minor once it meets the rule below.
- **Internal:** no longer exported, or exported but documented as unsupported.

**Rule for Stable.** An adapter is Stable when the shared conformance suite (`test/support/conformance.ts`) runs against the real engine, server or browser in CI, not only against a fake. The core contract, the wrappers and `createPersistence` are Stable because everything else builds on them.

This is a proposal. Nothing is removed or relabeled until it is approved.

## What the evidence shows

- **Every release so far shipped between 2026-10-14 and 2026-10-18.** Versions 0.1.0 to 0.14.0 are five days old (0.15.0 followed the next day). No entry point has had time in other people's hands, so the rule above rests on tests, not on soak time.
- **The contract has barely changed.** Between 0.1.0 and now the only change to `StorageAdapter` is the optional `list` method. `StoreResult`, `StoredValue` and `StoreErrorCode` are as they were. Later releases added entry points and options, and fixed bugs found in review. No changelog entry is labelled as breaking.
- **Evidence differs by adapter.** It falls into three tiers, set out in the table below.

**Why the three Experimental entry points.** Their evidence is a vendor emulator or a fake, and each depends on an SDK that changes its own major versions (`firebase-admin`, the Firebase web SDK, `supabase-js`). They move to Stable once they have been run against the production service and one SDK major version change has gone through without breaking them.

## Type exports

- **Option and result types** (`...Options`, `Loaded`, `Saved`, `Persistence`, `ConflictPolicy`, and the like): Stable alongside the function that takes them.
- **Structural driver types** (`PostgresClientLike`, `SqliteDatabaseLike`, `RedisClientLike`, `FetchLike`, `IdbFactoryLike`, `FileSystemLike` and the other `...Like` types): these are the library's contract with each driver. Keep them exported. They are Stable for Stable adapters, with one rule written into the policy: adding a required member to a `...Like` type is a breaking change. The real driver types must keep type-checking against them without casts.

## Findings

1. **The Stable list is broad.** Fourteen of the seventeen entry points meet the rule, which is more than the "core contract and a short list" I expected. The evidence in this repo is strong. The risk is that none of it has been used outside CI.
2. **Five helpers to remove.** `utf8Length`, `firestoreDocumentId`, `firestorePrefixUpperBound`, `realtimeNodeKey` and `keyFromRealtimeNodeKey` become Internal. Removing them is breaking, which is fine in 0.x.
3. **No `exports` gaps found.** Each of the 16 subpath entry points has both an `exports` and a `typesVersions` entry, as the ROADMAP's ground rules require. I did not rebuild and diff the published `dist/`.
4. **Missing for 1.0:** a versioning and support policy and a `SECURITY.md`. The repo has neither. The README is excluded from Prettier, so changes to it need care.
5. **Dependents.** `chat-and-react` uses only Stable exports here (`localStorageAdapter`, `sessionStorageAdapter`, `indexedDbAdapter`, `memoryAdapter`, `withPrefix`, and the contract types). Its dependency range is `^0.5.0`, which on 0.x never reaches a later minor.

## Decisions needed

1. Approve the Stable and Experimental split above.
2. Is the `restAdapter` test against an in-process fake enough for Stable?
3. Keep `keysWithPrefix` and `DEFAULT_MAX_BYTES` public, or make them Internal?
4. Remove the five Internal helpers from the entry points in 0.15, before 1.0?
